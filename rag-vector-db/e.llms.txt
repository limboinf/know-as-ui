## 知识库动态维护 —— 规避新旧版本冲突与版本幻觉

知识库上线只是数据生命周期的起点。以典型的业务规则变更为例：当退款期限从 7 天调整为 14 天，若更新流水线仅做简单的追加写入，问答系统极易出现同一问题在「7 天」与「14 天」之间随机摇摆、答案互相矛盾的现象。

这并非大模型的推理缺陷，而是底层数据同步机制的缺失。原型阶段通常只关注单向写入（解析、分块、嵌入、入库）；而进入生产环境后，源头数据持续变更，系统必须完整处理四类变更形态：

① 新增（Insert）

新文档录入。必须保证写入幂等性，避免重试或定时拉取导致同一文件重复灌库并生成冗余副本。

② 修改（Update）

历史切块必须下线，新切块同步写入。若仅追加写入，新旧版本将同时驻留并在检索中互斥冲突。

③ 删除（Delete）

源头文档废弃下线后，关联切块需及时清理，防止失效规则继续被大模型引用。

④ 架构迁移（Reindex）

更换嵌入模型、调整分块策略或更换数据库。历史向量全部失效，需执行零停机整库重建。

C 页第 6 章剖析了向量数据库内核如何处理物理写入与垃圾回收（增长段、墓碑与 Compaction）；本页则聚焦应用层同步流水线的设计：如何保证「向量库中的索引视图与业务源头实时保持严格一致」。

## 增量更新流水线 —— 块级哈希对比与精确重嵌入

定时清空整库全量重建在千级小规模数据下尚可支撑；但当语料体量增长至数百万乃至千万级切块时，全量重新嵌入带来的算力账单、长达数小时的构建耗时与可用性抖动均无法承受。增量同步流水线的核心目标，是在源文档变更时精准识别差异，**仅针对实际发生内容变动的切块执行向量重算**。

### 第一步：数据源变更捕获机制（CDC / 事件 / 水位线）

| 捕获方式 | 技术原理 | 核心优势 | 工程挑战与局限 |
| --- | --- | --- | --- |
| **全量扫描 + 哈希对比** | 定时计算全量源文档内容哈希，与上次快照对比 | 最稳健，可可靠发现源头删除 | 源端规模庞大时，扫描与哈希计算本身成为瓶颈 |
| **时间戳水位线（Watermark）** | 增量拉取 `updated_at > 上次水位` 的记录 | 实现简单、网络与计算开销极低 | 无法感知物理删除；时钟回拨或未单调递增可能漏检 |
| **CDC / Binlog 变更流** | 监听数据库底层 WAL 日志（如 Debezium） | 毫秒级准实时捕获，删除事件天然可追踪 | 引入额外基础设施，维护成本与链路复杂度较高 |
| **Webhook / 事件推送** | 内容管理系统（Notion / Confluence / CMS）主动推送变更事件 | 按需触发、零冗余轮询 | 网络抖动可能丢失事件，必须配备兜底对账机制 |

工业实践中的主流架构组合：**以事件驱动或 CDC 承接日常近实时增量更新，以每日定时全量哈希对账作为最终一致性兜底保障**。

### 第二步：块级 Diff 与分块边界稳定性

一篇文档仅修改个别语句，绝不意味着全篇必须全量重新计算嵌入向量。通过为每个切块计算独立的内容哈希（Content Hash），比对新旧切块集合即可复用未变更切块。然而，增量效率高度敏感于切块算法：**固定窗口切块极易引发切块边界的雪崩式漂移**。

### 第三步：确定性唯一 ID 与幂等写入

若切块 ID 依赖数据库自增序列或随机 UUID，重复执行同步流水线将导致同一切块被重复插入。采用**基于文档唯一标识与切块内容哈希衍生的确定性 ID（Deterministic ID）**，可确保相同内容在多次执行中永远产出相同的唯一标识，赋予写入操作天然的幂等性（Idempotence）：

sync.py · 幂等增量同步核心实现

```
import hashlib, uuid

def chunk_id(doc_id, text):
    h = hashlib.sha256(text.encode()).hexdigest()[:16]
    # Qdrant / Milvus 等系统支持 UUID 或整型，利用 uuid5 将字符串稳定映射为 UUID
    return str(uuid.uuid5(uuid.NAMESPACE_URL, f"{doc_id}:{h}")), h

def sync_doc(doc, store, embed):
    new = {}
    for seq, text in enumerate(split_by_structure(doc.text)):
        cid, h = chunk_id(doc.id, text)
        new[cid] = dict(text=text, doc_id=doc.id, seq=seq, content_hash=h,
                        version=doc.version, updated_at=doc.updated_at)

    old = set(store.ids_where(doc_id=doc.id))      # 基于元数据检索该文档的历史切块 ID
    add = [c for c in new if c not in old]

    vecs = embed([new[c]["text"] for c in add])  # 仅对新增哈希块调用模型计算
    store.upsert(ids=add, vectors=vecs, payloads=[new[c] for c in add])
    # 未变更切块：直接复用已有向量，仅刷新顺序与版本等元数据
    store.set_payload([c for c in new if c in old], new)
    store.delete(ids=list(old - new.keys()))       # 先写新块、后删失效块，避免查询出现空窗
```

上述抽象逻辑与具体数据库解耦（pgvector、Milvus、Qdrant 均原生提供按 ID upsert、元数据过滤及按 ID 批量删除）。业务层应当完全掌控这一同步控制逻辑，而非将其隐式绑定至特定上层框架。

### 框架内置的状态同步与映射表机制

主流开发框架普遍采用在外置存储中维护状态映射表的设计思路：记录切块哈希、数据源与写入时间，用以辅助推导需写入与需删除的切块集合。

| 框架方案 | 核心机制 | 源头删除识别能力 |
| --- | --- | --- |
| **LangChain** `index()` + RecordManager | 支持 `cleanup="incremental"`（按来源淘汰旧版本）与 `cleanup="full"`（清除批次外所有文档）模式 | 仅在 `full` 模式下自动清理，前提是单次调用必须传入完整数据集，传入子集将引发误删 |
| **LlamaIndex** `IngestionPipeline` + docstore | 基于持久化 docstore 对比哈希；提供 `UPSERTS_AND_DELETE` 策略自动清理未出现文档 | `UPSERTS_AND_DELETE` 可识别删除；要求 docstore 跨次调度持久化存储 |
| **Haystack** `DocumentWriter` | 提供 `OVERWRITE`（覆盖）、`SKIP`（跳过）与 `FAIL`（冲突报错）等主键写入策略 | 不支持自动清理源头删除，变更检测与删除生命周期需由外部应用编排 |

**状态存储与向量库双重状态隐患**：框架的持久化记录表与实际向量库属于两个独立存储系统。若有外部任务绕过框架直接写入向量库，状态表将对这部分数据失去追踪，导致其成为永久无法清理的孤儿数据。

### 专有增量同步数据流引擎选型

除轻量框架外，当业务面临多源异构数据、秒级高频变动或严格数据血缘审计需求时，开源生态提供了更高抽象层级的专有同步方案：

| 方案架构 | 代表开源项目 | 增量维护机制 | 适用场景与考量 |
| --- | --- | --- | --- |
| **增量数据流引擎** | **CocoIndex**（Rust 内核 + Python） | 采用声明式目标态模型并追踪数据血缘，源文件或分块逻辑变更时仅增量重算受影响节点 | 适合多源异构、需要完整数据血缘审计与流水线声明的场景 |
| **Pathway**（微分数据流引擎） | 基于 Differential Dataflow 持续监听数据源，感知变更并执行流式解析、向量化与索引更新 | 适合秒级高频流式同步；需注意商业部署协议约束 |
| **Pixeltable**（多模态声明式表） | 将嵌入索引建模为表的计算列，行级增量更新自动触发下游级联重算 | 适合多模态（图像、音频、文本）数据统一管理场景 |
| **库内触发机制** | **pgai Vectorizer**（Timescale） | 基于 PostgreSQL 触发器捕获行变更并推入工作队列，外部 worker 异步向量化 | 业务主数据已托管于 PostgreSQL，追求极简技术栈与事务联动 |
| **ELT 管道工具** | **Airbyte**（向量库目标端） | 提供 Incremental Append + Deduped 模式，借助源端主键在向量库执行去重维护 | 数据源分布于各类 SaaS 平台（Salesforce、Notion 等），需利用成熟连接器生态 |
| **端到端引擎** | **RAGFlow** | 系统内置多源连接器与增量同步机制，开箱即用 | 偏向完整开箱即用产品，不希望自研中间层编排代码 |

**选型考量**：若核心数据已托管于 PostgreSQL，优先采用 pgai Vectorizer；外部 SaaS 数据源优先结合 Airbyte；需要复杂数据流血缘审计时评估 CocoIndex；常规中小规模应用采用确定性 ID 与应用层轻量同步即可高效落地。

**工具边界与治理底线**：任何上层工具均无法替代三项底层工程设计：决定局部变更半径的分块结构稳定性、删除事件向下游缓存的级联失效、以及模型升级时全库重建的平滑演进方案。

大白话
按固定字数切块就像按固定厘米数剪布料，开头多出一小截，后面每一刀的切口位置全都会整体错位，整匹布的所有碎块都必须重做。按自然段落切，每段自成一体，修改哪一段就只需要重新处理哪一段。

## 写入一致性与删除治理 —— 消除时序空窗与孤儿数据

文档更新包含「下线旧版本切块」与「写入新版本切块」两个离散步骤。在缺乏跨行原子事务支持的向量存储中，操作时序直接决定了查询端的可见性：执行期间可能遭遇短暂的文档缺失（可用性空窗）或新旧版本并存（事实冲突）。此外，若同步进程在执行中途异常中断，必须保障系统具备可恢复性与最终一致性。

| 写入策略 | 瞬态可见性（中间态） | 中途异常中断后的状态 | 适用架构与选型 |
| --- | --- | --- | --- |
| **先删后写** | 存在数据空窗：窗口期内完全检索不到该文档 | 最危险：文档从索引中彻底丢失，直到下个全量同步周期 | 生产环境严禁采用 |
| **先写后删** | 短暂存在新旧版本共存；可通过查询端按版本号去重消除冲突 | 残留历史切块，可通过幂等重试或周期性对账完全修复 | 无跨行事务保证的独立分布式向量库（Milvus / Qdrant 等） |
| **事务机制 / 版本指针** | 强一致原子可见，无中间态：查询要么全部命中旧版，要么全部命中新版 | 历史版本继续稳定生效，未提交的新切块回滚或作为孤儿数据清理 | 关系型扩展（PostgreSQL / pgvector 单事务提交）；或业务层版本路由指针 |

pgvector · 单事务原子替换

```
BEGIN;
DELETE FROM chunks WHERE doc_id = 'D6';
INSERT INTO chunks (doc_id, version, seq, content, embedding, updated_at)
VALUES ('D6', 2, 0, '...', '[...]', now()),
       ('D6', 2, 1, '...', '[...]', now());
COMMIT;   -- 外部并发会话严格保证原子可见：要么全量 v1，要么全量 v2
```

这是关系型增强存储在更新治理上的显著架构优势：向量切块与业务数据完全处于同一 ACID 事务边界内。而在多数专用向量数据库中，通常需依靠「先写新块、后删旧块 + 查询侧版本过滤」或应用层版本路由指针来达成近似一致性。

### 删除治理：多级失效与最终一致性保障

在生产系统中，数据删除往往更容易被忽视。未彻底清理的作废文档不会直接报错，而是以陈旧知识的形式滞留于索引中，持续引发模型错误引用。可靠的删除机制必须建立四重保障：

① 变更事件联动

源端触发删除事件（CDC / Webhook），同步服务基于 doc_id 批量下线关联切块。具备准实时性，但需防御事件丢包。

② 周期性差集对账

定期拉取源端有效 doc_id 全集与向量库现有 ID 全集求差集，主动清理滞留孤儿切块。这是保障一致性的最后防线。

③ 存储物理回收

多数向量库删除操作仅标记软删除墓碑（Tombstone），需定期触发 Compaction 或 VACUUM 释放底层物理存储与内存（参见 C 篇第 6 章）。

④ 下游缓存多级失效

删除操作必须级联同步至语义缓存、答案缓存、BM25 全文索引及应用查询缓存，杜绝历史缓存污染。

**分布式写入可见性延迟**：即使客户端写入时序完全正确，分布式向量数据库在完成写入至索引可检索之间，仍存在由一致性模型（强一致、有界过时、最终一致）所决定的可见性窗口期。排查「刚完成同步却检索不到新内容」时，应首先确认节点间同步与索引刷新延迟。

**查看参考答案**
大白话
先删后写就像先拆旧招牌再挂新的，中间有一段时间完全没有招牌，如果挂新招牌时工人中途跑了，门口就彻底空了。先写后删就像先挂新招牌再拆旧招牌，中间虽有两块并存，但不会出现断档。对账就像巡店巡检，把遗漏未拆的旧招牌定期彻底清走。

## 模型升级与整库重建 —— 零停机平滑迁移（蓝绿切换）

当新一代嵌入模型在基准评测上带来显著召回提升时，系统无法采取增量过渡方式（即仅对新增文档采用新模型、旧文档保留历史向量）。不同嵌入模型所构建的高维几何流形完全异构，即使向量维度一致，其坐标分量与内积距离亦毫无数学可比性。模型升级必须执行全库重新嵌入。在保障线上服务不中断的前提下，蓝绿架构（Blue-Green Deployment）与集合别名（Collection Alias）是实现平滑切换的标准方案。

不同模型的向量空间在几何上互不兼容。模型 A 与模型 B 输出的高维向量指向不同的正交语义空间，其相似度度量完全失效。因此：**查询向量与候选文档向量必须严格源自同一模型**。更换嵌入模型或调整分块策略，本质上等同于整库全量重建。

全量重建通常需要数小时乃至数天时间，期间线上检索服务必须持续可用。工业界的标准落地模式是**蓝绿切换**：保留当前在线集合持续承接查询，在旁路独立创建新集合并执行全量回填，待基准评估通过后执行毫秒级原子切换，且保留快速回滚能力。核心基础设施工具是*集合别名（Collection Alias）*：应用层始终面向稳定的逻辑别名发起查询，底层路由目标可原子变更。Milvus、Qdrant、Elasticsearch 等均原生支持别名机制。

**高风险盲区：仅切换存储别名，未同步切换查询编码模型**：集合别名可在底层原子地重定向检索流量，但若应用层查询端仍在使用旧嵌入模型，系统将以旧模型向量检索新模型集合。由于维度相同不触发语法报错，系统将静默返回毫无语义关联的随机排序结果。生产发布必须保证「存储别名重定向」与「查询编码模型版本」原子协同生效。稳妥架构是将模型版本绑定于集合元数据中，应用层根据别名解析动态路由匹配模型。

Milvus · 别名原子切换与回滚

```
from pymilvus import MilvusClient
c = MilvusClient(uri="http://localhost:19530")

# 初始化：应用层面向逻辑别名 kb_prod
c.create_alias(collection_name="kb_v1", alias="kb_prod")

# kb_v2 基于新模型完成历史回填、影子评估通过后：原子重定向，无需修改应用代码
c.alter_alias(collection_name="kb_v2", alias="kb_prod")

# 异常处置：毫秒级原子回滚（确保观察期内尚未物理释放 kb_v1）
c.alter_alias(collection_name="kb_v1", alias="kb_prod")
```

PostgreSQL / pgvector 原生不提供集合别名概念，工业实践通常采用以下方案：在原表中增加 `embedding_v2` 向量列，后台异步填充并使用 `CREATE INDEX CONCURRENTLY` 并发建索引，完成后通过配置中心切换查询列名；或建立独立的新表，利用 SQL View（视图）作为逻辑别名完成秒级定义切换。

## 元数据架构与健康体检 —— 全生命周期资产治理

高可靠的增量同步、版本仲裁与安全控制，均建立在规范的块级元数据基础之上。向量本身仅是高维连续坐标，无法自解释其业务属性。来源溯源、版本控制、模型绑定与访问策略必须由结构化元数据承载。在建库初期确立严格的元数据规范，是避免后期索引失控与数据沼泽的关键保障。

### 推荐的块级核心元数据规范

| 元数据字段 | 核心治理用途 | 缺失造成的工程后果 |
| --- | --- | --- |
| `doc_id` · `seq` | 文档级粒度替换与级联删除；相邻上下文窗口拼接 | 无法按文档精确更新，任何微小变更只能全量重建 |
| `content_hash` | 块级 Diff 变更检测与内容去重 | 无法识别内容复用，增量同步退化为全量重嵌入 |
| `version` · `updated_at` | 查询端版本仲裁、多版本冲突解决、时效性监控 | 新旧版本冲突时缺乏事实裁决依据 |
| `source` · `source_url` | 生成答案权威溯源引用、周期性差集对账、按业务源批量下线 | 无法引用原文出处，无法与上游主数据对账 |
| `acl` / `tenant_id` | 检索层强制多租户与权限过滤隔离 | 产生数据越权泄露风险（参见 D 篇第 3 章） |
| `embed_model` · `chunker_version` | 标识嵌入模型与分块版本；识别混合异构向量脏数据 | 新旧模型向量意外混合驻留，导致整体召回悄然劣化 |
| `expires_at` | 限时公告、促销政策等到期自动淘汰机制 | 已失效的过期内容继续被大模型引用误导用户 |

**核心资产原则：原始文本是核心资产，向量仅为可再生的派生缓存**：禁止在存储中丢弃原始文本而仅保留向量。当面临模型迭代、切块调整或答案归因排查时，均需要原始文本作为基准输入。明确这一原则后，嵌入模型升级本质上属于派生缓存的重新预热，而非高风险的数据迁移。

### 合规要求与数据被遗忘权落地

当依据 GDPR 第 17 条等法规要求落实个人信息被遗忘权时，仅在向量库执行删除并不完备。数据副本通常分散存在于：原始语料存储、BM25 全文索引、语义缓存、问答访问日志、基准评估集、微调训练集以及快照备份中。企业需建立明确的「数据流向与血缘拓扑表」，明确各副本的保留周期与级联销毁责任，确保删除具备可审计性。

## 生产排障手册 —— 现象速查与分层定位矩阵

在前文技术架构的基础上，本章系统梳理 RAG 生产运行中最为高频的异常现象。通过建立「表象症状 → 底层根因 → 验证手段 → 处置方案」的分层诊断矩阵，帮助工程师快速定位问题发生的协议层（数据层、分块层、检索层、排序层、生成层或基础设施层），实现标准化排障闭环。

**更新同一个问题，答案时新时旧**
根因新旧版本的块同时在库，相似度几乎相同，排名随机抖动。
解法先写后删 + 查询端按 (doc_id, 最高 version) 去重；或事务 / 版本指针；跑一次对账清理残留。

**更新文档已经下线，还在被引用**
根因删除没有传播到向量库（只做了新增和修改的同步），或删除事件丢失。
解法接入删除事件 + 每日全量 doc_id 对账；LangChain 用 cleanup="full"，LlamaIndex 用 UPSERTS_AND_DELETE。
回看E 页 · 写入一致性与删除

**更新每次增量更新几乎都在全量重嵌入**
根因固定长度切块的边界漂移：插入或删除一段后，下游所有块的 hash 都变了。
解法改用结构感知切块；块 ID 用内容 hash 生成；只为新 hash 调用嵌入。
回看E 页 · 增量更新流水线

**更新换了嵌入模型后召回大幅下降**
根因新旧模型的向量混在同一个索引里，或别名切了但查询仍用旧模型。
解法整库重嵌入到新集合；查询模型与集合的 embed_model 绑定；切换前在黄金集上做影子评估。
回看E 页 · 模型升级与重建

**更新不想自己写同步脚本，有没有现成的**
根因增量同步 = 变更检测 + 记账 + 调度 + 对账，自己写容易漏掉删除。
解法按场景选：Postgres 用 pgai Vectorizer；多源加血缘用 CocoIndex；SaaS 源用 Airbyte Deduped 模式；轻量场景用 LangChain / LlamaIndex 记账。
回看E 页 · 增量同步数据流引擎

**更新同一份文件被导入了两次**
根因块 ID 是自增或随机生成的，重复执行不幂等。

回看E 页 · 确定性唯一 ID

**运维删了大量数据，磁盘和内存都没降，查询还变慢**
根因删除只打墓碑，图节点和段仍在。
解法批量删除后触发 Compaction（Milvus / Qdrant）或 VACUUM（Postgres）。
回看C 页 · 写入与新鲜度

回看C 页 · HNSW

**运维内存不够，向量放不下**
根因float32 全量向量 + HNSW 图常驻内存。

回看C 页 · 量化

**检索错误码、型号、人名搜不到**
根因纯向量检索对精确标识符不可靠。

回看B 页 · 混合检索与 RRF

**检索用户口语化提问，召回很差**
根因查询和文档的用词差距太大；一句话包含多个意图。

回看B 页 · 改写问题

**检索加了过滤条件后结果变少，甚至为空**
根因HNSW 先搜后过滤，过滤选择性高时 top-k 被过滤光。

解法给块加标题路径前缀，或上下文化检索（为每块生成一句背景说明再嵌入）。
回看B 页 · 切块

**排序正确的块在候选里，但没进 top-k**
根因一阶段相似度排序不够精细。
解法加交叉编码器重排：先召回 50，重排后取 5。
回看B 页 · 重排

**排序加了重排反而变差**
根因块长度超过重排器的最大输入，被静默截断，答案在被截掉的部分。
解法检查重排器的 max length；控制块大小；对长块分段打分取最大值。
回看B 页 · 重排截断

**数据top-k 被几乎一样的内容占满**
根因同一内容在多个文档里复制粘贴（模板、FAQ 转载）。
解法入库按 content_hash 去重，近似重复用 MinHash；检索侧用 MMR 增加多样性。
回看E 页 · 元数据与健康体检

**数据PDF、表格解析出来是乱码或错行**
根因版面解析能力不足，表格被拍平成一行文字。
解法换版面感知的解析工具；表格单独转成 Markdown 或结构化记录再入库；入库前抽样人工检查。
回看B 页 · 切块

**生成库里明明没有，模型却硬答**
根因不管相关度多低，top-k 总会返回 k 条，模型被迫基于无关内容作答。
解法设相似度 / 重排分数阈值，低于阈值走「不知道」兜底；提示词允许拒答。
回看A 页 · 向量会翻车

**生成检索到的内容互相矛盾**
根因多个版本或多个来源说法不一。
解法先治理（删旧版本）；提示词里附上 updated_at 和来源，要求以最新、最权威来源为准并标注分歧。
回看E 页 · 元数据与健康体检

**生成回答没有出处，没法核对**
根因提示词里没有给块编号，也没要求引用。
解法给每块编号，要求模型引用编号，回答时映射回文档链接与段落。
回看D 页 · 上线四件事

**安全用户看到了无权查看的文档内容**
根因权限在生成层做（让模型别说），或文档 ACL 变更没有同步到块元数据。
解法检索层按身份过滤；ACL 变更当成一次文档更新处理；缺 ACL 的块默认拒绝。
回看D 页 · 权限

**安全文档里藏了指令，模型照做了**
根因间接提示注入：检索到的内容被模型当成指令。
解法提示词里明确「资料只是数据」；入库时扫描可疑指令；高风险动作不允许由检索内容触发。
回看D 页 · 上线四件事

**安全用户要求删除个人数据**
根因数据有多个副本：原文、向量、全文索引、缓存、日志、评估集、备份。
解法维护数据流向清单，删除按清单逐项执行并留审计记录。
回看E 页 · 数据被遗忘权落地

**评估改了参数，不知道是变好还是变坏**
根因没有带标注的黄金集，只能凭几个例子感觉。
解法建 50–200 条黄金集，每次改动跑 Recall@k、MRR 与回答忠实度做回归。
回看B 页 · 评估

**评估离线指标很好，线上用户还是不满意**
根因黄金集不代表真实问题分布。
解法定期从线上日志抽样补充黄金集；监控无答案率、点踩率、追问率。
回看E 页 · 核心监控指标

分层架构：数据接入（解析与去重）· 更新运维（新鲜度、删除、模型升级）· 分块策略 · 检索召回 · 排序打分 · 文本生成 · 访问安全 · 底层运维 · 评测验证。同一异常现象可能存在多重诱因，优先排查链路靠前且验证成本最低的环节。

**排障第一性原理：确定性样本与基准切块**：定位 RAG 检索异常时，首要条件是获取可稳定复现的查询输入与预期命中的真实切块。具备这两项输入即可在各层逐级验证相似度得分与排序衰减，在数分钟内排查出根因节点；缺乏标准样本时，盲目调整模型与提示词往往适得其反。这也是前文强调黄金测试集为核心工程资产的根本原因。

**查看参考答案**
大白话
以新上线系统为例，最常见的三类问题为：文档更新后仍命中陈旧答案、专业编码/型号精确词无法召回、未命中相关资料模型依然强行作答。验证手段分别为：核对库内该 doc_id 的多版本存活切块；单独触发 BM25 稀疏检索验证词法分词；检查最高检索重排得分是否触发兜底拒答阈值。
